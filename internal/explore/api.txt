dnscount explorer API
=====================

dnscount explore serves the LAN table explorer (GET /) and this API. It
reads the live database read-only, with its own explore.db (feed matches,
the indicator index) attached. All GET, all JSON, no auth: Caddy only
exposes it to the LAN.

Conventions
-----------
  since   how far back to look. 24h, 90m, 7d, an RFC 3339 time
          (2026-10-27T00:00:00Z), or a date (2026-10-27, local time).
          Omitted = all time, unless an endpoint says otherwise.
  limit   max rows. Omitted or 0 = 100.
  times   JSON times are UTC, RFC 3339 with nanoseconds.
  status  on /api/hits: a code (404) or a class (4xx).
  errors  plain text body. 400 = bad parameter, 404 = no such thing,
          500 = server error, 503 = the query ran past -query-timeout.

Rows that carry an address or domain also carry what's known about it:
  "verdict"   worst verdict of the lists it's on now: malicious|suspicious|info,
              or "reserved" for a reserved special-purpose address or name
              (RFC 6890 ranges such as 192.0.0.170, ipv4only.arpa): not a
              real host, so never flagged, whatever lists include it
  "special"   for special-purpose addresses and names: {"name","rfc","note",
              "reserved"}. Translation prefixes (NAT64 64:ff9b::/96, Teredo,
              6to4) are context only and keep their verdicts.
  "feeds"     those lists, as feed:<name>
  "asn", "as_owner", "country"   from iptoasn

Rows with intel can also carry "queried": outside services' cached answers,
  {"internetdb"|"abuseipdb"|"censys": {"found", "as_of", "facts"}}
facts by provider: internetdb {ports, hostnames, cpes, tags, vulns};
abuseipdb {score, reports, users, last_reported, usage, isp, domain, tor};
censys hosts {services: [{port, protocol, software}], dns_names, asn,
as_name, country, city, labels, threats, vulns, reputation, greynoise};
censys domains {port, software, labels, threats, cert_names, cert_issuer}.
They're context, never verdicts. /api/health has "lookups": each service's
units used (24h, this month), cached answers and last error.

Records
-------

/api/hits?[site=][&ip=][&status=][&since=][&limit=]
  Recent hits, newest first.
  [{"id","ts","site","source","client_ip","forwarded_for","method","host",
    "path","query","status","bytes","user_agent","referer"}]
  query and referer: values of credential-looking parameters (api_key,
  ApiKey, token, access_token, X-Emby-Token, ...) are stored as REDACTED.
  source is one of:
    counter     counted by the counter endpoints
    middleware  sent to /ingest by a Go app
    caddy       read from a Caddy JSON access log
    access-log  read from an nginx/apache access log

/api/alerts?[ip=][&action=allowed|blocked][&by=signature|src|dst|category|action][&since=][&limit=]
  The router's IDS/IPS alerts, newest first. ip= matches either end.
  [{"id","ts","src_ip","src_port","dst_ip","dst_port","proto","action",
    "signature","signature_id","category","severity","source","src_hits",
    "direction","src_name","src_mac","dst_name","dst_mac","policy"}]
  direction, *_name, *_mac, policy: from UniFi's CEF events (empty for
  Suricata JSON). They name the LAN device, since CEF often has no
  address for it. by= also takes direction, policy, src_name, dst_name.
  action: allowed (detected only) or blocked (dropped by the router).
  src_hits: requests that source made to our sites over the same period.
  With by=, counts instead: [{"key","count","first"}].

/api/bans?[ip=][&jail=][&since=][&limit=]
  fail2ban bans, newest first, each paired with the unban that ended it.
  [{"id","banned_at","unbanned_at","jail","ip","ports","bantime_ns","failures",
    "hits_24h_before","hits_during","restored"}]
  hits_during: requests from that IP that reached a site on a port the ban
  covers while it was in force (after a 5s grace for requests already in
  flight). Anything above 0 means the block leaked.
  ports: the jail's ports (empty = all). restored: true when fail2ban
  re-applied the ban after a restart (it was unbanned in the same jail
  within 30s before): the ban before it continuing, not a new one.

/api/trips?[ip=][&breaker=counter|ingest|syslog|syslog-not-allowed][&since=][&limit=]
  Circuit-breaker trips, newest first (without the detail blob).
  [{"id","tripped_at","cooldown_until","ended_at","breaker","key","reason",
    "window_events","window_bad","suppressed_during_cooldown",
    "first_seen_in_window"}]
  key is who tripped it (an IP, or "*" when too many IPs were tracked).
  reason: rate (too many requests), map_full, or the kind of bad request
          that tipped it over: bad_token | malformed | oversize | not_allowed

/api/trips/{id}
  One trip, plus "detail": everything recorded about the offender. That's
  request headers (Authorization/Cookie stored as a hash and length, never
  the value), body samples, parse errors, the last events, samples from
  during cooldown, the rate curve, reverse DNS, and what was already known
  about that IP.
  404 if there's no such trip.


Tables
------

/api/ips?[since=7d][&order=flagged|top|bottom|new|recent][&limit=100]
  Public addresses that hit our sites, were banned, raised IDS alerts,
  tripped a breaker or had a login refused. LAN devices (any address that
  used the router's DNS)
  never appear.
  [{"ip","hits","errors_4xx","first","last","sites","bans","leaks",
    "alerts_allowed","alerts_blocked","trips","auth_failures", ...intel}]
  auth_failures: logins an app refused (Jellyfin's log).

/api/ip/{ip}?[since=30d]
  One address: intel with every list row ("matches", including lists it
  dropped off), all-time counts, recent hits, bans, alerts, trips and
  refused logins ("auth_failures": [{"ts","source","ip","user"}]), router
  firewall lines with it at either end ("connections": [{"client_ip",
  "dst_ip","dst_port","proto","action","rule","count","first","last"}],
  busiest 200 groups), the
  names that resolved to it and which LAN clients looked them up, and AS
  changes. The address is re-matched against the current lists first.
  For a LAN address also:
    "device": {"ip","mac","name","hostname","alias","network","seen","source"}
      name is the alias set in UniFi if any (not its default
      "hostname xx:yy"), else the hostname. An IPv6 address is named
      through its MAC.
    "sightings": every DHCP lease, UniFi client event and neighbour-table
      entry for this address or any MAC seen at it, newest first.
    "lookups": [{"domain","count","first","last","flagged"}], what it
      looked up (busiest 500), flagged first: flagged = the domain, or an
      address it resolved to, is listed suspicious or worse.

/api/domains?[since=7d][&order=flagged|top|bottom|new|recent][&limit=100]
  Domains the LAN looked up.
  [{"domain","lookups","clients","first","last","blocked","new",
    "answers": {"verdict","feeds","ips"}, ...intel}]
  answers: listed addresses this name resolved to.

/api/domain/{domain}?[since=30d]
  One domain: intel, who looked it up (with subdomains), what it resolved
  to (each answer with its intel), logged connections to those addresses.

/api/clients?[since=7d]
  LAN devices: lookups, distinct domains, new domains, flagged domains
  (directly or through what they resolved to) with up to 5 examples.
  Each also has "name", "mac" and "network" when a sighting (below) ties
  its address to a device.

/api/flagged?[since=30d][&verdict=malicious,suspicious|all|reserved][&limit=100]
  Every listed indicator seen in the window, worst and newest first.
  verdict=reserved (alone or with others) adds special-purpose addresses
  and names, which are never flagged otherwise; they sort last.
  [{"indicator","kind","direction": in|out|both,"first_seen","last_seen",
    "hits","sites","bans","alerts","clients":[{"ip","name","count"}],
    "via_domains", ...intel}]

/api/overview
  Rows per table (all-time and last 24h), indicators indexed, flagged
  count, and the background loops' last run.

/api/health
  Thresholds, the latest sample, data checks (cached 10 minutes), breaker
  stats from the live admin listener, slowest requests of the last hour,
  and each feed: entries, version, last good fetch, age, stale (no good
  fetch in 3 intervals), skipped (e.g. a missing key), errors, and
  outdated_rows (rows in the 90-day window not yet checked against the
  current version; 0 a minute after each update).

/api/health/series?[since=6h][&points=360]
  Samples taken every 15s (kept 24h, in memory): WAL size, PSI
  (cpu/memory/io), load, available memory, per-unit CPU %, memory and
  pressure, explorer request p95/max and timeouts, newest DNS lookup and
  hit age. Thinned to points= by keeping each bucket's worst values.

Bans: every address that carries intel also has "bans_30d", how many times
fail2ban banned it in the last 30 days across all jails (the window it
doubles repeat bans over). A ban fail2ban re-applies after a restart (an
unban of the same address and jail within 30s before it) isn't counted: on
/api/bans those rows have "restored": true.
